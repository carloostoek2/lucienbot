## Threat Model

### Trust Boundaries
1. **Admin boundary:** Only `bot_config.ADMIN_IDS` members can access `/admin` panel. Admin handlers (in 17-03) must check `is_admin()` on every callback.
2. **User boundary:** Any Telegram user can play trivia and reach streak milestones. No auth gate beyond Telegram ID.
3. **Database boundary:** 4 new tables store promotion config, generated codes, and redemption records. No PII beyond `user_id` (Telegram user ID).
4. **Scheduler boundary:** APScheduler DateTrigger jobs (in 17-02) fire with bot context; scheduler job handlers must not trust caller context.

### STRIDE Threat Register

| ID | Threat | STRIDE Category | Mitigation |
|----|--------|----------------|------------|
| T-17-01 | Non-admin user accesses streak promotion management callback data (`streak_promo_create`, `streak_promo_list`, `streak_promo_view`) | Elevation of Privilege | `is_admin()` check via `lambda cb: is_admin(cb.from_user.id)` on ALL admin callback handlers (17-03) |
| T-17-02 | Malformed callback data with spoofed `promo_id` or `level_id` (e.g., `streak_promo_delete_99999`) | Tampering | Validate `promo_id` exists in DB before any action; return LucienVoice error if not found. Service methods (`activate`, `deactivate`, `delete`) query promotion first and return None/raise on missing |
| T-17-03 | Duplicate code claim (user hits same streak level twice, e.g., day 1 and day 2) | Tampering | DB unique constraint `uq_streak_redemption_user_level` on (user_id, level_id) + server-side `_has_claimed_level()` check before delivery |
| T-17-04 | Code guessing / brute force of discount codes | Information Disclosure | Codes use `secrets.token_hex(6)` = 128 bits of entropy. Format `SK-{12 hex chars}` = ~2.8 x 10^14 possible codes per prefix. Practically unguessable |
| T-17-05 | Race condition: two concurrent trivia answers for same user trigger double claim on same level | Tampering | `claim_for_streak()` executes check-and-deliver atomically within a single DB transaction. `_has_claimed_level()` reads inside the same transaction as the write |
| T-17-06 | Promotion deleted while scheduled activation job still exists in APScheduler | Denial of Service | `delete_promotion()` in 17-02 also calls `scheduler.remove_streak_promotion_jobs(promo_id)` to clean up orphan jobs |
| T-17-07 | Category deactivation collision: promotion auto-deactivates a category that another active promotion also uses | Tampering | `deactivate()` in 17-02 checks: "does any other active promotion use this category?" If yes, skips category deactivation. If no, calls `TriviaCategoryService.deactivate()` |

### Standard Mitigations (inherited from project)
- All admin handlers check `is_admin()` via lambda on `F.data` filter
- All DB operations use SQLAlchemy ORM (no raw SQL)
- APScheduler uses `SQLAlchemyJobStore` for persistent jobs
- `ThrottlingMiddleware` rate-limits all user handlers (admin bypass)
- Callback data uses explicit prefixes (`streak_promo_`) with server-side validation
